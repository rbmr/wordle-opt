# Example policy trees

Example policy trees for the viewer. All three cover the **full**
2340-candidate set with the full 14,855-word guess list: `optimal` is the exact
optimum (total cost 8001), and the two heuristics are cheaper policies included
for comparison.

| file | strategy | candidates | nodes | max depth | total cost | mean guesses |
|------|----------|-----------:|------:|----------:|-----------:|-------------:|
| `optimal.json` | `optimal` | 2340 | 2478 | 5 | 8001 | 3.419 |
| `min-remaining.json` | `min-remaining` | 2340 | 2934 | 4 | 8561 | 3.659 |
| `max-freq.json` | `max-freq` | 2340 | 2908 | 8 | 9545 | 4.079 |

## How they were generated

```bash
# heuristics: the full candidate set (about a second each)
for s in min-remaining max-freq; do
  cargo run --release -- solve --strategy "$s" \
    --output "site/examples/$s.json" --no-progress
done

# optimal: the full tree, written by the `full` run on the compute host (see
# AGENTS.md's "The `full` run: at most once a day"); copy it in from
# ~/optimal-2340.json there.
```

Each file embeds the guess and candidate lists, so it is self-contained: the
viewer (and `wordle-opt validate <file>`) can check it with no other files
present.

Each `.json` also has a sibling `.js` (`window.WordleExamples["<name>"] = ...`)
which is what the viewer's example buttons load. It is generated from the
`.json` and exists so the examples work when `site/index.html` is opened
directly from disk, where `fetch()` of a sibling file is blocked by the
browser:

```bash
for n in optimal min-remaining max-freq; do
  node -e 'const fs=require("fs");const n=process.argv[1];const j=fs.readFileSync(n+".json","utf8").trim();
  fs.writeFileSync(n+".js","window.WordleExamples=window.WordleExamples||{};window.WordleExamples[\""+n+"\"]="+j+";\n")' "$n"
done
```

The optimal tree's total cost (8001) is independently checked: the full run
validates the written tree (edge iff possible at every node, every candidate
terminates) before reporting success, and `solve --compare` cross-checks a
tree's cost against a cost-only solve of the identical candidate set whenever
one is built from a subset.

## Other word lengths

The viewer derives the word length from the tree, so it also renders and plays
trees for other letter counts. Three small synthetic examples are included to
demonstrate this:

| file | letters | candidates | nodes |
|------|--------:|-----------:|------:|
| `letters3.json` | 3 | 36 | 50 |
| `letters4.json` | 4 | 36 | 42 |
| `letters6.json` | 6 | 36 | 40 |

These are **not** produced by the Rust engine - `core::Word` is `[u8; 5]`, so
`wordle-opt` itself only solves and validates 5-letter dictionaries (it reports
a clear error for other lengths rather than misbehaving). They are generated by
`generate_letter_examples.js`, a small dependency-free Node script that builds a
greedy min-remaining tree and computes the dictionary hash with the same FNV-1a
encoding the Rust side uses:

```bash
node site/examples/generate_letter_examples.js
```

## The full optimal tree

`optimal.json` is the real thing: the exact optimal policy for all 2340
candidates - 2478 nodes, maximum depth 5, total cost 8001 (mean 3.419 guesses).
It was generated on the compute host by the `full` run in **4.28 hours**
(15,413.7s), which also exported its progress series
(`~/optimal-2340-progress.parquet`).

The viewer handles trees of any size. The browser renderer expands lazily.
